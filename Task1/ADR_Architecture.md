# Architectural Decision Record (ADR): Обеспечение отказоустойчивости и масштабируемости InsureTech

## Контекст

Текущая архитектура представляет собой единую точку отказа (SPOF): одна зона доступности, единственный экземпляр БД на VM, отсутствие географической оптимизации доставки контента.

**Требования бизнеса:**
*   Доступность: 99.9%
*   RTO (Recovery Time Objective): 45 мин.
*   RPO (Recovery Point Objective): 15 мин.
*   География: Клиенты по всей РФ (требуется низкая задержка загрузки).
*   Объём данных: ~50 GB.

## Предлагаемое решение (To-Be)

Мы переходим к архитектуре **Single Region, Multi-AZ**.

*   **Уровень приложения:** Active-Active — все три зоны одновременно обслуживают трафик.
*   **Уровень базы данных:** Active-Standby (Primary + Standbys) с автоматическим failover.

### 1. Вычислительные ресурсы (Kubernetes)

*   **Конфигурация:** Один растянутый кластер Kubernetes разворачивается поверх трёх зон доступности (Availability Zones: A, B, C).
*   **Обоснование выбора единого кластера:** При текущем объёме данных (50 GB) и развёртывании в одном регионе независимые кластеры в каждой зоне создают избыточную операционную сложность. Единый кластер обеспечивает общую плоскость управления, единый набор RBAC-политик и автоматическое перераспределение подов средствами Kubernetes Scheduler.
*   **Масштабирование:**
    *   **HPA (Horizontal Pod Autoscaler):** Автоматически увеличивает количество подов приложений при росте нагрузки (CPU/Memory/RPS).
    *   **Cluster Autoscaler:** Автоматически добавляет новые Node (VM) в кластер, если поды не помещаются на текущих узлах.
*   **Отказоустойчивость:** При отказе одной зоны Kubernetes автоматически перераспределяет поды в выжившие зоны (Self-Healing). Сервис продолжает работу без ручного вмешательства.

### 2. База данных (PostgreSQL)

*   **Конфигурация:** Кластер PostgreSQL (Patroni или Managed Service for PostgreSQL) в конфигурации **1 Primary + 2 Standby**.
*   **Распределение:** Узлы БД разнесены по разным зонам доступности (Primary в Zone A, Sync Standby в Zone B, Async Standby в Zone C).
*   **Репликация:**
    *   **Sync Standby (Zone B):** Синхронная репликация гарантирует, что транзакция подтверждается только после записи на Primary и Sync Standby. Это обеспечивает **RPO ≈ 0**.
    *   **Async Standby (Zone C):** Асинхронная репликация обеспечивает дополнительную копию данных с минимальной задержкой (обычно < 1 сек), не влияя на latency записи.
    *   Такая конфигурация (quorum-based: 1 sync из 2 standbys) означает, что при потере Sync Standby система автоматически промотирует Async Standby в Sync, сохраняя гарантию RPO ≈ 0.
*   **Read/Write Splitting:** Для снижения нагрузки на Primary read-запросы направляются на реплики. Приложения используют отдельные connection strings для чтения и записи.
*   **Failover:** Автоматическое переключение мастера (Patroni / Managed failover) занимает < 2 минут. Требование RTO < 45 мин выполняется с большим запасом.
*   **Бэкапы:** WAL-логи непрерывно стримятся в S3 Object Storage для обеспечения Point-in-Time Recovery (PITR).

### 3. Шардирование

Шардирование базы данных **не применяется**. Текущий объём данных составляет ~50 GB, что комфортно укладывается в возможности одного кластера PostgreSQL (рекомендуемый порог — до нескольких TB). Введение шардирования на данном этапе создаст значительную операционную сложность (distributed transactions, cross-shard queries) без ощутимого выигрыша в производительности.

Решение будет пересмотрено при:
*   Росте объёма данных свыше 500 GB.
*   Появлении требований к горизонтальному масштабированию записи (write-heavy workload).

### 4. Сеть и доставка контента

*   **Load Balancer (L7):** Application Load Balancer распределяет входящий API-трафик между подами во всех зонах. Он выполняет **Health Checks** (HTTP GET /healthz, интервал 5 сек, порог отказа — 3 проверки подряд). При недоступности подов в зоне трафик автоматически перенаправляется в оставшиеся зоны.
*   **CDN (Content Delivery Network):** Статический контент (JS, CSS, изображения) хранится в Object Storage (S3) и раздаётся через CDN. CDN выполняет Origin Pull непосредственно из S3, минуя ALB, что снижает нагрузку на балансировщик. Пользователи из Владивостока загружают интерфейс с ближайшего Edge-сервера, а не из Москвы.

### 5. Фейловер-стратегия (клиент → приложение)

Фейловер на уровне взаимодействия клиента с приложением реализуется следующим образом:

1.  ALB непрерывно выполняет HTTP Health Check (`GET /healthz`) ко всем подам.
2.  При отказе зоны ALB исключает недоступные поды из пула маршрутизации за ~15 секунд (3 неудачных проверки × 5 сек интервал).
3.  Kubernetes Scheduler автоматически перезапускает поды в оставшихся зонах.
4.  Клиент не замечает отказа — переключение прозрачно, соединение устанавливается с одним из здоровых подов.

**Итого RTO приложения:** ~15 сек (на уровне маршрутизации) + время поднятия дополнительных подов (< 1 мин).
**Итого RTO БД:** < 2 мин (автоматический failover Patroni / Managed Service).

### 6. Соответствие требованиям

| Параметр | Требование | Решение | Результат |
| :--- | :--- | :--- | :--- |
| **Доступность** | 99.9% | Multi-AZ (3 зоны) + L7 Balancer + Health Checks | **Выполнено** (Типичный SLA для Multi-AZ > 99.95%) |
| **RTO** | 45 мин | ALB failover ~15 сек + Auto-failover БД < 2 мин + K8s Self-healing | **Выполнено** (< 5 мин) |
| **RPO** | 15 мин | Sync Replication (quorum) + WAL Archiving | **Выполнено** (~0 сек) |
| **География** | Быстрая загрузка | CDN + S3 Origin | **Выполнено** |
| **Шардирование** | — | Не требуется при 50 GB | **Решение зафиксировано** |

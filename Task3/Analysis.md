# Анализ проблем и рисков текущей архитектуры InsureTech

## Контекст

InsureTech планирует подписать агентское соглашение ещё с **пятью** страховыми компаниями (итого — **десять**). Текущая архитектура взаимодействия между сервисами основана на синхронном REST и polling. Ниже — анализ проблем и рисков, связанных с планируемым ростом.

---

## Проблема 1. Линейный рост латентности в ins-product-aggregator

**Текущее поведение:**
Сервис `ins-product-aggregator` при каждом входящем REST-запросе синхронно обращается ко всем страховым компаниям, агрегирует ответы и возвращает единый список. Время ответа определяется **самой медленной** компанией: `latency ≈ max(latency_1, latency_2, ..., latency_N)`.

**Риск при росте:**
При 5 компаниях вероятность того, что хотя бы одна ответит медленно или с ошибкой, уже ненулевая (команда фиксирует такие инциденты). При 10 компаниях эта вероятность удваивается. Если хотя бы одна компания отвечает с таймаутом (например, 30 секунд), весь запрос висит 30 секунд — и все потребители (`core-app`, `ins-comp-settlement`) блокируются.

**Формально:** Вероятность отказа хотя бы одного API при N независимых компаниях: `P(fail) = 1 - (1 - p)^N`. При `p = 2%` (типичная ошибка внешнего API): 5 компаний → 9.6%, 10 компаний → 18.3%.

**Влияние:** Деградация UX для клиентов (медленная загрузка тарифов), рост числа ошибок в логах, возможные каскадные таймауты.

## Проблема 2. Temporal Coupling через Polling

**Текущее поведение:**
- `core-app` запрашивает `ins-product-aggregator` каждые **15 минут** (polling).
- `ins-comp-settlement` запрашивает `ins-product-aggregator` раз в **сутки** (ночью).
- `ins-comp-settlement` запрашивает `core-app` раз в **сутки** для получения оформленных страховок.

**Риски:**

*Устаревшие данные.* core-app показывает клиентам тарифы с задержкой до 15 минут. Если страховая компания изменила цену — клиент может оформить страховку по устаревшим условиям. При росте числа компаний и частоты обновлений тарифов вероятность таких рассогласований растёт.

*Суточная задержка взаиморасчётов.* ins-comp-settlement получает данные о продуктах раз в сутки. Если в течение дня тарифы изменились — реестр взаиморасчётов может быть сформирован на основании неактуальных данных.

*Суточная задержка по оформленным страховкам.* ins-comp-settlement запрашивает все оформленные за день страховки батчевым REST-запросом раз в сутки. Это означает задержку до 24 часов между оформлением и появлением страховки в системе взаиморасчётов.

## Проблема 3. Каскадные отказы

**Текущее поведение:**
Взаимодействие между сервисами — синхронное (REST). Цепочка зависимостей:

```
Клиент → InsureTech Web → core-app → ins-product-aggregator → 5 (10) страховых компаний
```

**Риск:**
Если `ins-product-aggregator` недоступен или одна из страховых компаний «тормозит» — `core-app` получает ошибку или таймаут. Пользователь не может увидеть список продуктов. Поскольку `core-app` блокируется на синхронном вызове, его потоки (threads) заняты ожиданием ответа. При исчерпании пула потоков — `core-app` перестаёт обслуживать и другие запросы (не связанные с тарифами).

При 10 компаниях поверхность атаки для каскадных отказов удваивается.

---

## Проблема 4. Batch-зависимость ins-comp-settlement → core-app

**Текущее поведение:**
`ins-comp-settlement` раз в сутки делает REST-запрос к `core-app` для получения **всех** оформленных за день страховок.

**Риски:**

*Рост объёма данных.* С ростом числа клиентов (планируемая рекламная кампания) количество оформленных за день страховок будет расти. Батчевый REST-запрос с большим response body увеличивает риск таймаута и потребление памяти.

*Хрупкость.* Если запрос упал (сетевая ошибка, таймаут, рестарт `core-app` в момент запроса) — `ins-comp-settlement` не получает данные за день. Нужен механизм retry или ручного перезапуска.

*Отсутствие real-time.* Бизнес не может видеть актуальное состояние взаиморасчётов в течение дня — только после ночного батча.

---

## Проблема 5. Масштабирование числа потребителей данных

**Текущее поведение:**
`ins-product-aggregator` обслуживает REST-запросы от `core-app` (каждые 15 мин) и `ins-comp-settlement` (раз в сутки). Каждый потребитель polling'ит независимо.

**Риск:**
При появлении новых сервисов-потребителей (например, аналитический сервис, сервис уведомлений) каждый из них будет добавлять свой polling к `ins-product-aggregator`, увеличивая нагрузку линейно. `ins-product-aggregator` при каждом запросе синхронно дёргает все 10 компаний — нагрузка на внешние API также растёт.

| # | Проблема | Вероятность | Влияние | Приоритет |
|:---|:---|:---|:---|:---|
| 1 | Линейный рост латентности (10 компаний, синхронно) | Высокая | Высокое (UX, таймауты) | 🔴 Критический |
| 2 | Устаревшие данные из-за polling (15 мин / 24 ч) | Высокая | Среднее (бизнес-ошибки) | 🟡 Высокий |
| 3 | Каскадные отказы (синхронная цепочка) | Средняя | Высокое (полная недоступность) | 🔴 Критический |
| 4 | Batch-запрос страховок (хрупкость, рост объёма) | Средняя | Среднее (задержка взаиморасчётов) | 🟡 Высокий |
| 5 | Линейный рост нагрузки при добавлении потребителей | Низкая (пока) | Среднее | 🟢 Средний |

## Предлагаемое решение: переход на Event-Driven Architecture

### Ключевые изменения

1. **Внедрение Message Broker (Apache Kafka).** Асинхронный обмен событиями между сервисами вместо синхронного polling.

2. **ins-product-aggregator → push вместо pull.** Сервис сам по расписанию собирает данные из 10 страховых компаний и публикует событие `ProductsUpdated` в Kafka-топик. Потребители подписаны и обновляют свои локальные реплики в near real-time.

3. **core-app → публикация событий при оформлении страховки.** При оформлении страховки `core-app` публикует событие `InsuranceIssued`. `ins-comp-settlement` подписан на этот топик и получает данные в real-time (вместо суточного batch).

4. **Transactional Outbox для core-app.** Оформление страховки (запись в `core-db`) и публикация события `InsuranceIssued` должны быть атомарны. Используется паттерн Transactional Outbox: событие записывается в outbox-таблицу в той же транзакции, relay-процесс (Polling Publisher) отправляет в Kafka.

### Что остаётся синхронным (REST)

- `InsureTech Web` → `core-app` — пользовательские запросы (нужен мгновенный ответ).
- `InsureTech Web` → `client-info` — CRUD клиентских данных.
- `core-app` → `client-info` — получение данных клиента при оформлении.
- `ins-product-aggregator` → страховые компании — внешние API (мы не контролируем протокол).
- `core-app` → Платёжный сервис — оплата страховки.
- `ins-comp-settlement` → страховые компании — передача реестров.

### Что переводится на Event-Streaming

| Взаимодействие (As-Is) | Паттерн (To-Be) | Топик Kafka | Стиль |
|:---|:---|:---|:---|
| `core-app` polling `ins-product-aggregator` (15 мин) | Подписка на событие | `products.updated` | Event-Carried State Transfer |
| `ins-comp-settlement` polling `ins-product-aggregator` (1 раз/сутки) | Подписка на событие | `products.updated` | Event-Carried State Transfer |
| `ins-comp-settlement` polling `core-app` (страховки за день) | Подписка на событие | `insurance.issued` | Event-Carried State Transfer |

### Решение по Transactional Outbox

| Сервис | Нужен Outbox? | Обоснование |
|:---|:---|:---|
| `core-app` | **Да** | Оформление страховки (запись в БД) + публикация `InsuranceIssued` должны быть атомарны. Потеря события = финансовые последствия. |
| `ins-product-aggregator` | **Нет** | Данные получены из внешних API, нет БД-транзакции. Публикация идемпотентна (UPSERT тарифов). Retry на уровне Kafka producer достаточно. |

### Ожидаемый результат

| Метрика | As-Is | To-Be |
|:---|:---|:---|
| Актуальность тарифов в core-app | до 15 мин задержки | секунды (near real-time) |
| Актуальность страховок в ins-comp-settlement | до 24 ч задержки | секунды (near real-time) |
| Устойчивость к отказу 1 из 10 компаний | Весь запрос падает | Данные 9 компаний доступны, 1 обновится позже |
| Добавление 11-й компании | Изменения в core-app и ins-comp-settlement | Только в ins-product-aggregator |
| Добавление нового сервиса-потребителя | Новый polling → нагрузка на aggregator | Новый consumer group → нагрузка = 0 |
